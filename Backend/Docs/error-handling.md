# Global Error Handling & 404 - Changes Summary

This document summarizes the recent backend changes that add a centralized Express error handler and a JSON 404 responder, and how to use and test them.

## Why
- Prevent unhandled exceptions (Prisma errors, rejected promises, etc.) from crashing the Node process.
- Standardize JSON error responses across the API.

## Files changed
- [Backend/src/server.ts](Backend/src/server.ts): Added imports for `Request`, `Response`, `NextFunction`, registered a catch-all 404 handler and a global error handler (Express recognizes it by having exactly 4 arguments). The error handler logs the error and returns a formatted JSON response via `sendError`.
- [Backend/src/controllers/ProductController.ts](Backend/src/controllers/ProductController.ts): Updated route handlers to accept `next: NextFunction` and forward errors using `next(err)` instead of responding directly in catch blocks.
- [Backend/src/controllers/CategoryController.ts](Backend/src/controllers/CategoryController.ts): Same changes as above.
- [Backend/src/controllers/CartController.ts](Backend/src/controllers/CartController.ts): Same changes; service-specific errors (e.g., PRODUCT_NOT_FOUND, OUT_OF_STOCK) are converted to Error objects with `status` codes before calling `next(err)`.
- [Backend/src/controllers/StoreController.ts](Backend/src/controllers/StoreController.ts): Forward errors to `next(err)` (preserve status when available).
- [Backend/src/utils/response.ts](Backend/src/utils/response.ts): Existing helpers `sendError`, `sendNotFound`, `sendServerError` are reused by the new global handler and the 404 responder. (No API change to these helpers.)

## Behavior
- Unknown routes now return a JSON 404 response: `{ success: false, message: "Route /api/nonexistent not found", code: 404 }`
- Any thrown error or rejected promise that reaches the global handler will result in a JSON response whose status code is `err.status || err.statusCode || 500` and message is either the error message (in development) or `Internal Server Error` (in production).
- The global handler logs the error to the server console: `console.error(`[ERROR] ${req.method} ${req.originalUrl} >>`, err);`

## How to test locally
1. From repository root:
```bash
cd Backend
npm run dev
```
2. Verify 404 JSON response:
```bash
curl -i http://localhost:3000/api/nonexistent
```
Expect 404 JSON with message: `Route /api/nonexistent not found`.

3. Verify 500 JSON response (temporary test route):
- Option A (quick & reversible): add a test route in `server.ts` before the 404 handler:
  ```ts
  app.get('/api/_test/error', () => { throw new Error('test error'); });
  ```
- Call it:
```bash
curl -i http://localhost:3000/api/_test/error
```
Expect 500 JSON (message `test error` in development, `Internal Server Error` in production).

4. Verify controllers forward errors: call an existing endpoint that triggers a DB error (e.g., missing required field) and observe a 4xx/5xx JSON formatted response.

## Developer guidance / conventions
- Controllers and middleware should forward unexpected errors with `next(err)` rather than sending responses directly. This centralizes formatting and logging.
- For expected client errors, create an Error with a `status` property (e.g., `const err: any = new Error('Not found'); err.status = 404; next(err);`). The global handler will use that status code.
- Consider adding a typed `AppError` class in a follow-up to standardize error shapes: `{ message, status, code, details? }`.
- Audit middleware (e.g., `tenant.middleware.ts`, validators, upload handlers) and convert direct `sendServerError`/`res.*` responses in catch blocks to `next(err)` where appropriate. This was not fully completed in the current change.
